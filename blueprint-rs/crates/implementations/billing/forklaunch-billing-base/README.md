# Billing persistence

With the `postgres` feature, `PostgresBillingStore::migrate` applies migrations using a schema owner. Runtime stores require a separate role without SUPERUSER/BYPASSRLS and an explicit tenant. Sensitive provider fields and session URLs remain encrypted; plaintext reads require an audit context.

Migration 5 adds an administrative Stripe identity foundation. `StripeBindingScope::administrative` explicitly names the deployment label, account ID and live/test mode. This is trusted server configuration: the current Stripe transport does not authenticate this scope, and API key prefixes or client-provided `providerFields` must not supply it.

`provision_stripe_binding` requires an existing durable checkout, payment-link or portal record, an explicit public UUID, provider reference, and nonblank actor/correlation context. It preserves existing storage keys and encrypted fields. Cache-only ownership is rejected. Public, storage and scoped provider references cannot be duplicated. `stripe_binding_by_public_id` and `stripe_binding_by_provider_id` require the exact tenant/account/mode/deployment/kind context. `revoke_stripe_binding` accepts the opaque generation returned by provisioning or lookup; a stale generation cannot revoke a replacement. Provisioning and revocation commit with their audit records.

Grant the administrative role schema USAGE, SELECT/UPDATE on `fl_billing.records`, SELECT/INSERT/DELETE on `fl_billing.provider_bindings`, and SELECT/INSERT on `fl_billing.provider_binding_audit`. UPDATE on ownership records permits `SELECT ... FOR UPDATE`. The audit table has only tenant-scoped SELECT/INSERT RLS policies, so non-bypass runtime roles cannot update or delete audit rows even with broader table grants. Schema owners retain normal administrative control. Revoke the binding before deleting its durable record; the foreign key intentionally restricts deletion while an alias exists.

These APIs expose no HTTP route, make no provider calls, and perform no automatic migration/backfill. Existing service wrappers, webhooks and checkout reconciliation still use their original IDs. Binding lookup results are snapshots, not financial-operation capabilities. Authenticated provider-context verification, wrapper integration, cache ownership/expiry and portal replacement are separate work; the foundation alone does not establish runtime TypeScript/Rust identity parity.
